# 코칭 엔진 재설계 — 루브릭 요소 기반 판정/미션 구조

> **상태: 설계 진행 중.** 1~5번 항목은 사용자와 합의 완료, 6번(프롬프트 문안)은 1단계 초안까지,
> 7번(평가셋)은 미착수. 아래 "아직 안 정한 것" 참고.

## 배경

현재 코칭은 `lib/coaching.js`의 프롬프트 두 개(`buildFirstRoundPrompt` / `buildRevisionPrompt`)가
Gemini를 **한 번** 호출해 잘한 점 1개 + 보완점 2개를 **자유 생성**하는 구조다. 문제는 세 가지다.

1. **기준이 매번 흔들린다.** "보완할 점 2가지를 알려줘"는 자유 생성이라 같은 글에 같은 미션이 나오지
   않고, 교육과정과의 정합성을 보장할 방법이 없다. 장르별 지침(`GENRE_COACHING_GUIDANCE`)은 한 줄짜리
   힌트일 뿐 판정 기준이 아니다.
2. **판정과 작문이 한 호출에 섞여 있다.** `temperature: 0.7` 하나가 판정에도 적용되어 라운드마다
   판정이 튄다. 두 작업은 요구가 정반대다 — 판정은 일관성, 작문은 다양성.
3. **도달도가 글의 상태와 무관하다.** `computeNextAttainment`는 40%에서 시작해 반영한 보완점 수 ×10%를
   더할 뿐이고 상한이 없어 100%를 넘는다. 이 때문에 레퍼런스 디자인의 도달도 눈금을 구현하지 못하고
   미뤄둔 상태다(`docs/PROJECT_STATUS.md`의 "범위 밖으로 남긴 것" 참고).

목표는 **교육과정 해석은 사람이 하고, LLM은 그 기준을 적용만 하는** 구조로 바꾸는 것이다.

## 핵심 원칙

- **코드는 "무엇을 볼지"를 정하고, LLM은 "이 글에서 그게 어떤지"만 본다.**
  요소 목록·우선순위·미션 개수·도달도 계산은 전부 코드. 요소 충족 여부와 미션 문장만 LLM.
- **LLM에게 숫자를 묻지 않는다.** 판정은 열거형으로만 받고 숫자는 코드가 계산한다.
- **"이전보다 나아졌나?"를 LLM에게 직접 묻지 않는다.** 비교 질문은 LLM이 거의 항상 긍정한다.
  같은 요소표로 각 버전을 독립 판정하고 차이는 코드가 뺄셈한다.
- AI는 점수·등급·상중하를 만들지 않는다. 최종 평가는 교사가 한다. (기존 프로젝트 철학 유지)

## 1. 루브릭 요소 모델

장르마다 **5~6개**의 요소를 사람이 직접 설계한다. 요소 하나의 구조:

```js
{
  id: 'reading-scene',
  scope: '문단',        // 글 | 문단 | 문장   ← 미션 우선순위 1순위
  axis: '내용',         // 내용 | 구성 | 표현  ← 동점일 때 2순위
  label: '인상 깊은 장면',
  check: '책에서 인상 깊었던 장면이나 구절이 구체적으로 드러나는가?',
  missionSeed: '어떤 장면이 기억에 남았는지 고르고, 그 장면을 자세히 써보기',
}
```

- `check` — 1단계(판정) 프롬프트에 그대로 들어간다.
- `missionSeed` — 2단계(작문) 프롬프트에 들어가 **미션의 방향을 고정**한다. 방향은 사람이 정하고
  LLM은 학생 글의 문맥만 붙인다.
- `label` — 교사 체크리스트에 그대로 노출된다.

**요소 개수를 5~6개로 잡은 이유:** 3~4개면 도달도가 한 칸에 25~33%씩 튀고 미션 후보가 금방 바닥난다.
8~10개면 미션이 잔잔해지고 한 라운드에 10%밖에 안 올라 퍼드백이 지지부진해진다.

**`scope`를 `axis`와 별도 필드로 둔 이유:** 퇴고는 글 전체 → 문단 → 문장 순으로 해야 한다.
문장 다듬기부터 시키면 나중에 문단을 갈아엎을 때 그 작업이 버려진다.
정렬 순서(`글 → 문단 → 문장`)는 **코드 상수 하나로 분리**한다 — 지금은 고정값이지만, 교사가 활동별로
순서를 바꾸는 UI를 붙일 때 그 상수만 활동 설정으로 옮기면 되게 한다.

### 예시 — 독서감상문 (6학년 1학기 1단원)

| scope | axis | label |
|---|---|---|
| 글 | 구성 | 문단이 내용에 따라 나뉘어 있다 |
| 글 | 내용 | 책 내용과 내 생각이 구분된다 |
| 문단 | 내용 | 인상 깊은 장면을 구체적으로 썼다 |
| 문단 | 내용 | 그 장면에 대한 생각·느낌을 썼다 |
| 문단 | 내용 | 읽고 난 뒤 달라진 점·다짐 |
| 문장 | 내용 | 책 제목·지은이를 밝혔다 |

## 2. 요소 충족 판정 — 3단계

`check`의 답은 **충족(○) / 부분(△) / 미충족(✕)** 3단계로 받는다. 교사 체크리스트에도 △를 그대로 보여준다.

- "장면을 쓰긴 썼는데 구체적이지 않은" 상태가 초등학생 글에서 압도적으로 많다. 2단계면 이게 ✕로
  떨어져 아이가 좌절하거나, 반대로 LLM이 후하게 ○를 줘 도달도가 부풀려진다.
- LLM도 경계 케이스를 억지로 한쪽에 밀지 않아 판정이 더 안정된다.
- △는 점수가 아니라 상태이므로 "점수·등급을 만들지 않는다"는 원칙을 깨지 않는다.
- 로드맵의 "충족 여부 체크(O/X만)" 항목은 이 결정에 맞춰 수정한다.

## 3. 미션 2개 고르는 규칙

```
1. 미충족(△·✕) 요소만 후보
2. 정렬: scope(글→문단→문장) → △/✕ 섞기 → axis(내용→구성→표현)
3. 같은 요소를 이미 2회 연속 준 경우 맨 뒤로 강등
4. 상위 2개 선택
5. 후보 1개면 미션 1개만, 0개면 미션 없이 "완성!" 축하로 마무리
```

- **△/✕ 섞기**: 미션 2개 중 하나는 ✕(새로 쓰기), 하나는 △(다듬기)로 뽑는다. 둔 과제 하나 + 쉬운
  과제 하나라 한 라운드에 최소 하나는 성공하기 쉽다. 한쪽이 없으면 그냥 순서대로 둘을 뽑는다.
- **2회 연속 강등**: 같은 미션을 세 번째로 받는 아이는 그 미션을 이해하지 못한 것이라 반복해도 풀리지
  않는다. 다른 요소로 넘겼다가 나중에 돌아온다.
- **잘한 점 1개는 ○인 요소 중에서** 고르게 한다. 그래야 칭찬이 공허해지지 않는다. 다 ✕인 초기 글이면
  요소와 무관하게 칭찬하도록 예외를 둔다.

## 4. 미션 수행 판정

요소 판정과 **별개로** 미션마다 **완료 / 시도 / 안함**을 받는다. 같은 호출 안의 항목 추가라 비용은
늘지 않는다. "미션은 반영했는데 요소는 아직 △"인 아이에게 "잘 반영했어, 조금만 더"라고 말해주기 위한
근거이고, 교사 화면의 성실도 표시에도 쓴다.

세 장치를 겹친다.

**(1) 미션과 판정 기준을 같이 낳는다.** 2단계(작문)에서 미션 문장을 만들 때 `criterion`을 함께 뱉게 하고,
다음 라운드 판정 프롬프트에 그대로 넣는다. 이게 없으면 판정 시점의 LLM이 미션 문장을 제멋대로
재해석한다.

```js
{
  elementId: 'reading-scene',
  text: '주인공이 용감했다고 했는데, 어느 장면에서 그렇게 느꼈어? 그 장면을 자세히 써보자.',
  criterion: '주인공이 용감하게 행동한 특정 장면이 새로 서술되었는가',
}
```

**(2) 변경분을 직접 넣는다.** 현재는 이전 글 전체 + 새 글 전체를 던지고 LLM이 알아서 대조하게 둔다
(`lib/coaching.js:69-77`). 이미 프로젝트에서 쓰고 있는 `diffWords`로 **추가된 부분 / 지운 부분**을
서버에서 뽑아 별도 블록으로 넣는다.

**(3) 코드 게이트는 부정에만 쓴다.** 글이 전혀 바뀌지 않았으면 LLM 호출 없이 전부 '안함'으로 처리한다
— LLM은 안 바뀐 글에도 "고쳤네요!"를 곧잘 한다. 반대로 "그 자리가 바뀌었으니 수행했다"는 **긍정
증거로는 쓰지 않는다.** 아이가 다른 위치에 잘 쓴 경우를 놓치기 때문. 키워드 비교는 어느 방향으로도
쓰지 않는다.

## 5. 도달도 재정의

```
도달도 = Σ(요소 점수) / 요소 개수      (충족=1, 부분=0.5, 미충족=0)
```

- **미션 수행 판정은 이 숫자에 넣지 않는다.** 3단계 판정을 도입한 순간 ✕→△(+0.5), △→○(+0.5)로
  부분 진전이 이미 요소 점수에 반영되므로, 미션 반영률을 또 더하면 같은 노력을 두 번 세게 된다.
  미션 판정은 피드백 문구와 교사 화면 성실도에만 쓴다.
- **학생에게 보이는 값은 내려가지 않는다** (`max(역대 최고, 이번 라운드)`). 교사 화면은 이번 라운드의
  실제값을 그대로 보여준다. 평가가 아니라 퇴고 동기가 목적이므로 이 비대칭은 의도적이다.
- **기존의 40% 시작 바닥값은 없앤다.** 게이지가 "6칸 중 2칸"으로 보이면 0%보다 덜 아프고, 분량 미달
  글은 애초에 코칭이 실행되지 않는다.
- **덤:** 요소 기반이 되면 게이지 눈금이 곧 요소 6개가 된다. 레퍼런스 디자인의 도달도 눈금을 드디어
  구현할 수 있고, 아이가 "어느 칸이 아직 안 찼는지"를 눈으로 본다.

## 6. 2단계 파이프라인

에이전트도 RAG도 쓰지 않는다. 흐름이 완전히 결정적이고(입력·출력·순서 고정), 검색할 코퍼스가 없다
(요소표는 활동당 몇백 토큰이라 프롬프트에 다 들어간다). **고정된 2단계 체인**으로 간다.

| | 1단계 · 판정 | 2단계 · 작문 |
|---|---|---|
| 입력 | 요소표 + 학생 글 (+ 지난 미션·criterion·diff) | 1단계 결과 + 학생 글 |
| 출력 | boolean/열거형만, 자유 텍스트 없음 | 잘한 점 1 + 미션 2 + criterion 2 |
| temperature | 0 | 0.7 |
| 페르소나 | 없음 (확인자) | 디노 |

**경계를 여기 둔 이유:** 판정값은 도달도와 교사 체크리스트의 근거라 감사 가능해야 하고, 작문은 아이
말투라 다양성이 필요하다. 한 호출에 섞으면 둘 다 어중간해진다.

**3단계 이상으로 쪼개지 않는다.** "추출 → 판정 → 우선순위 → 생성 → 톤 조정"식은 단계마다 오류가
누적되고 디버깅이 어려워진다. 우선순위는 코드가, 톤은 2단계 프롬프트 안에서 처리한다.

**대가:** 호출이 2번이라 학생 체감 대기가 2~4초 → 4~7초로 늘어난다. 사용자가 이 대가를 인지하고
2단계를 선택했다. 필요해지면 나중에 1단계 결과(체크리스트·도달도)를 먼저 화면에 뿌리고 미션 카드를
이어서 띄우는 방식으로 체감을 줄일 수 있다.

### 6-A. 1단계 판정 프롬프트 (초안)

```
너는 초등학교 6학년 글쓰기 활동의 결과물을 정해진 기준표로 확인하는 역할이야.
글을 잘 썼는지 평가하거나 점수를 매기는 게 아니라,
기준표의 각 항목이 이 글에 나타나 있는지만 확인해.

[판정 기준]
- 충족: 그 항목이 분명하게, 구체적으로 드러난다.
- 부분: 있긴 하지만 한 문장뿐이거나 뭉뚱그려 표현되어 구체성이 부족하다.
- 미충족: 글에 아예 없다.

[판정할 때 지킬 것]
- 초등학교 6학년이 쓴 글이라는 걸 기준으로 삼아. 어른 글의 기준으로 보지 마.
- 후하게도 박하게도 판정하지 마. 있으면 있다고, 없으면 없다고만 해.
- 글에 담긴 생각이 옳은지 그른지는 판단하지 마. 항목이 나타나는지만 봐.

[확인할 항목]
1. 책 제목이나 지은이가 글에 나오는가?
2. 책에서 인상 깊었던 장면이나 구절이 구체적으로 드러나는가?
3. 그 장면에 대한 자신의 생각이나 느낌이 드러나는가?
4. 책의 내용과 자신의 생각이 구분되어 드러나는가?
5. 책을 읽고 난 뒤 달라진 생각이나 다짐이 드러나는가?
6. 문단이 내용에 따라 나뉘어 있는가?

[학생이 쓴 글]
---
{writing}
---

먼저 이 글이 자음/모음만 반복하거나 스페이스로 글자 수만 채우는 등
실제로 의미가 통하지 않는 글인지 판단해서 meaningless로 알려줘.
그렇지 않다면 항목 1~6을 각각 충족/부분/미충족으로 판정해.
```

재코칭 라운드에는 블록 세 개가 더 붙는다:

```
[지난번에 준 고치기 미션]
1. 미션: "..."
   확인 기준: "..."
2. 미션: "..."
   확인 기준: "..."

[이번에 새로 추가된 부분]      ← diffWords로 서버에서 추출
[이번에 지운 부분]

미션 1, 2가 각각 수행되었는지도 판정해.
- 완료: 확인 기준을 분명히 만족한다.
- 시도: 그 방향으로 고친 흔적이 있지만 확인 기준을 아직 만족하지 못한다.
- 안함: 관련된 변화가 없다.
```

**출력 스키마:** `{ meaningless, elements: [{ no, status }], missions: [{ no, done }] }`.
`status`만 담은 배열로도 되지만 `no`를 함께 받으면 순서가 어긋났을 때 코드가 검증할 수 있다.

**미해결:** "판정 기준" 세 줄이 사실상 이 앱의 채점 기준이고 LLM이 후해질지 박해질지가 여기서 갈린다.
특히 `부분`의 정의("한 문장뿐이거나 뭉뚱그려 표현되어 구체성이 부족하다")가 6학년 글에 실제로 쓸 만한
경계인지 교사 검토가 필요하다.

### 6-B. 2단계 작문 프롬프트 (미작성)

문안은 아직 쓰지 않았다. 담아야 할 것은 합의되어 있다.

- 디노 페르소나와 말투 규칙이 여기에 산다.
- 입력은 1단계 판정 결과(충족 요소 / 미충족 요소 + 해당 `missionSeed`)와 학생 글.
- `missionSeed`를 그대로 옮겨 적지 말고 **학생 글에 실제로 나온 내용을 인용해** 구체화하게 한다.
- 한 미션에 한 가지만 요구. 초등학생이 읽기 쉬운 길이.
- 잘한 점은 충족 요소 중 하나를 골라 **글의 어느 부분이 그런지 짚어서** 칭찬.
- 미션마다 `criterion`(다음 라운드 판정용, 학생에게는 안 보임)을 함께 생성.

## 7. 평가셋 (미착수)

아키텍처보다 이쪽이 중요하다. 실제 초등학생 글 20~30편(잘 쓴 것 / 못 쓴 것 / 애매한 것 / 무의미글 /
살짝만 고친 것)에 기대 판정을 사람이 붙여두고, 프롬프트를 바꿀 때마다 돌린다. 이게 없으면 "정교화"가
느낌에 그친다. Vitest는 이미 있으므로, 실제 API를 호출하는 회귀 검증은 `npm run eval` 같은 별도
스크립트로 분리한다(유닛테스트에 섞지 않는다).

- 독서감상문 외 장르의 요소표. 첫 구현은 어느 장르부터 할지.
- 요소 판정 결과의 저장 스키마 (기존 JSON 컬럼 재사용 여부).
- 평가셋 구성과 `npm run eval` 스크립트 (7).

## 다음 스펙으로 미룬 것 — 교사 루브릭 업로드

Phase 3의 나머지 절반(교사가 자기 루브릭을 표/이미지/텍스트로 올리는 기능)은 이 스펙에 넣지 않는다.
정규화 대상이 될 요소 스키마가 먼저 확정되어야 설계할 수 있기 때문. 다만 그때의 설계 방향은 이번
논의에서 이미 정해졌다.

- **교사 루브릭 원문을 코칭 프롬프트에 그대로 붙이지 않는다.** 교사 루브릭에는 "4점: 매우 우수" 같은
  채점 척도가 섞여 있어서, 붙이는 순간 AI가 점수를 매기기 시작한다.
- 업로드 시점에 **한 번만** LLM을 돌려 위 요소 스키마로 변환하고, **교사가 화면에서 확인·수정·확정**한다.
  AI는 초안만 만들고 확정은 사람이 한다(기존 프로젝트 원칙과 일치).
- 저장되는 것은 구조화된 데이터뿐. 코칭 시점 프롬프트는 교사 루브릭 유무와 무관하게 동일한 형태를
  유지한다.
- 교육과정 요소와 **병합하되 교사가 켜고 끈다.** 완전 대체는 교사가 적지 않은 기본기(분량·문단)를
  잃고, 순수 병합은 요소가 10개로 불어나 미션 2개 뽑기가 무의미해진다.
- **활성 요소 개수에 상한을 둔다(예: 최대 6개).** 그 이상이면 LLM 판정 품질이 떨어지고 도달도 분모도
  이상해진다.
