# 면담 보고서 루브릭 기반 Gemini 프롬프트 파일럿

## 상태와 목표

이 문서는 초등학교 6학년 2학기 2단원 `면담 보고서 쓰기`를 대상으로 하는 첫 번째
루브릭 기반 Gemini 코칭 파일럿의 확정 설계다.

현재 코칭은 Gemini 한 번의 호출에서 잘한 점 1개와 보완점 2개를 자유 생성한다. 파일럿은 이를
다음 두 단계로 분리한다.

1. 정해진 루브릭과 채점기준으로 학생 글을 판정한다.
2. 코드가 선택한 수정 대상에 맞춰 학생이 바로 실천할 수정미션을 작성한다.

학생 글을 점수화하거나 등급화하지 않는다. 루브릭은 큰 학습 목표이고, 채점기준은 Gemini가 학생
글에서 확인할 수 있는 관찰 가능한 행동이다.

## 적용 범위

- 기존 첫 번째 활동 카드를 `6학년 2학기 2단원 · 면담 보고서 쓰기`로 교체한다.
- 활동 선택 영역의 제목은 여러 학기가 섞여도 맞도록 `6학년 국어 활동 선택`으로 바꾼다.
- `면담 보고서` 장르만 새 2단계 코칭 파이프라인을 사용한다.
- 다른 장르는 기존 단일 호출 코칭을 유지한다.
- 첫 코칭과 재코칭을 모두 지원한다.
- 교사 루브릭 업로드와 다른 장르의 루브릭 전환은 이 파일럿에 포함하지 않는다.

## 루브릭과 3단계 채점기준

각 채점기준은 `충족`, `부분`, `미충족` 중 하나로 판정한다. 프롬프트와 저장 데이터는
`rubricId`와 `criterionId`를 함께 보존한다.

### 루브릭 1 · 면담의 목적과 대상이 분명하게 드러난다

#### `purpose` · 면담 목적을 밝혔다

- 충족: 누구에게서 무엇을 알아보기 위해 면담했는지 목적이 분명하다.
- 부분: 면담 주제나 관심사는 나오지만 무엇을 알아보려 했는지 모호하다.
- 미충족: 면담 목적을 식별할 수 없다.

#### `interviewee` · 면담 대상자를 밝혔다

- 충족: 대상자의 이름, 관계, 직업, 역할 중 식별 가능한 정보가 있다.
- 부분: 대상자를 언급하지만 “그분”, “어떤 사람”처럼 누구인지 알기 어렵다.
- 미충족: 면담 대상자를 식별할 수 없다.

### 루브릭 2 · 면담을 통해 얻은 정보를 구체적으로 전달한다

#### `new-fact` · 면담으로 새롭게 알게 된 사실을 제시했다

- 충족: 면담을 통해 새롭게 알게 된 사실을 하나 이상 명확히 제시한다.
- 부분: 정보는 있지만 면담으로 새롭게 알게 된 사실인지 불분명하다.
- 미충족: 새롭게 알게 된 사실을 식별할 수 없다.

#### `fact-detail` · 새롭게 알게 된 사실을 구체적으로 설명했다

- 충족: 새 사실과 함께 이유, 과정, 사례, 상황 중 하나 이상을 설명한다.
- 부분: 새 사실은 있으나 단순히 나열하거나 뭉뚱그려 표현한다.
- 미충족: 설명할 새 사실이 없거나 구체적인 설명을 찾을 수 없다.

### 루브릭 3 · 면담 보고서의 짜임에 맞게 내용을 구성한다

#### `opening` · 앞부분에 면담 목적, 대상, 준비 과정을 썼다

- 충족: 본격적인 면담 내용 전에 목적, 대상, 준비 과정이 소개된다.
- 부분: 앞부분은 있으나 세 내용 중 일부가 빠졌거나 위치가 불분명하다.
- 미충족: 면담 내용을 이해하기 위한 앞부분이 없다.

#### `body` · 가운데에 면담으로 새롭게 알게 된 사실을 썼다

- 충족: 새롭게 알게 된 사실이 글의 중심 내용으로 묶여 전달된다.
- 부분: 새 사실은 있지만 다른 내용과 뒤섞여 중심 내용을 파악하기 어렵다.
- 미충족: 가운데에 해당하는 면담 내용이 없다.

#### `closing` · 뒷부분에 면담 후 느낀 점을 썼다

- 충족: 글의 마무리에서 면담 후 든 생각, 느낌, 변화를 구체적으로 밝힌다.
- 부분: 느낌이 짧거나 막연하거나 글의 중간에만 흩어져 있다.
- 미충족: 면담 후 느낀 점을 찾을 수 없다.

### 공통 판정 원칙

- 맞춤법이나 문장이 미숙해도 내용을 식별할 수 있으면 그 이유로 낮게 판정하지 않는다.
- 사실의 옳고 그름이나 학생 생각의 수준을 평가하지 않는다.
- 학생 글에 직접 드러난 내용만 사용하고 추측하지 않는다.
- `opening`, `body`, `closing`은 내용의 존재보다 배치와 흐름을 중심으로 본다.
- 제목이나 줄바꿈이 없어도 내용상 역할이 구분되면 구조가 있다고 인정한다.
- `new-fact`가 미충족이면 `fact-detail`은 충족일 수 없다.

## 2단계 코칭 파이프라인

### 1단계 · 판정

판정 프롬프트는 다음을 입력으로 받는다.

- 활동 주제
- 위 루브릭과 채점기준의 3단계 행동 앵커
- 현재 학생 글
- 재코칭이면 직전 글, 직전 미션과 확인 기준, 추가·삭제된 변경분

출력은 JSON 구조화 응답이다.

```js
{
  meaningless: false,
  criteria: [
    {
      rubricId: 'purpose-and-subject',
      criterionId: 'purpose',
      status: 'met' // met | partial | unmet
    }
  ],
  priorMissions: [
    {
      missionId: '...',
      status: 'done' // done | attempted | not-done
    }
  ]
}
```

판정에는 자유로운 코칭 문장을 포함하지 않는다. `temperature`는 `0`으로 고정한다. 글이 전혀 바뀌지
않은 재코칭은 Gemini를 부르기 전에 코드가 이전 미션을 모두 `not-done`으로 처리한다.

### 코드 · 수정 대상 선택과 통합

Gemini에게 “가장 중요한 기준”을 자유롭게 고르게 하지 않는다. 코드는 판정 결과에서 `partial`과
`unmet` 기준을 가져와 최대 2개의 수정 대상을 결정한다.

선택 원칙:

1. `unmet`을 `partial`보다 먼저 다룬다.
2. 보고서의 핵심 정보인 `new-fact`와 `fact-detail`을 가장 먼저 다룬다.
3. 면담 맥락인 `purpose`와 `interviewee`를 다음으로 다룬다.
4. 글의 마무리인 `closing`을 다음으로 다룬다.
5. 내용은 있으나 위치와 흐름이 어색할 때 `opening`과 `body`를 다룬다.
6. 같은 수정 대상이 2회 연속 제시되었으면 다른 후보 뒤로 강등한다.

중복·선후관계 통합:

- `new-fact`와 `fact-detail`이 모두 부족하면 하나의 핵심 내용 미션으로 묶는다.
- `purpose`와 `interviewee`가 모두 부족하면 하나의 도입 미션으로 묶을 수 있다.
- 내용 자체가 없는 경우 같은 내용을 요구하는 `opening` 또는 `body` 구조 미션은 별도로 선택하지 않는다.
- 구조 기준은 필요한 내용이 있으나 배치와 흐름이 불분명할 때 독립 미션이 된다.
- 통합 미션은 서로 무관한 일을 한꺼번에 요구하지 않는다. “새 사실을 고르고 그 사실을 뒷받침하는
  내용을 덧붙이기”처럼 하나의 결과를 완성하기 위한 짧은 연속 단계만 허용한다.

### 2단계 · 디노 코칭 문장 생성

작문 프롬프트는 다음을 입력으로 받는다.

- 현재 학생 글
- 1단계의 충족 기준
- 코드가 선택하고 통합한 수정 대상 최대 2개
- 각 수정 대상의 사람 작성 미션 방향
- 재코칭이면 이전 미션 수행 상태

출력은 JSON 구조화 응답이다.

```js
{
  strength: {
    rubricId: '...',
    criterionId: '...',
    text: '...'
  },
  missions: [
    {
      id: '...',
      rubricIds: ['...'],
      criterionIds: ['...'],
      text: '...',
      criterion: '...'
    }
  ],
  complete: false
}
```

작성 원칙:

- 잘한 점은 충족 기준 하나와 학생 글의 실제 내용을 연결해 칭찬한다.
- 충족 기준이 하나도 없으면 글을 끝까지 작성한 노력처럼 루브릭 판정을 왜곡하지 않는 칭찬을 한다.
- 수정미션은 학생이 바로 고칠 수 있는 핵심 결과 하나에 집중한다. 통합 미션에서는 그 결과를 만들기
  위한 짧은 연속 단계를 안내할 수 있다.
- 학생 글의 실제 내용을 짚되 글에 없는 면담 내용이나 사실을 만들어내지 않는다.
- 완성 문장, 모범답안, 그대로 베낄 예시는 대신 써주지 않는다.
- 질문이나 단서는 사용할 수 있지만 학생이 채워야 할 내용을 남겨둔다.
- 서로 같은 행동을 요구하는 미션 두 개를 만들지 않는다.
- 초등학교 6학년이 한 번 읽고 이해할 수 있는 길이와 어휘를 사용한다.
- 각 미션과 함께 다음 라운드에서 사용할 관찰 가능한 `criterion`을 생성한다.
- 수정 후보가 없으면 미션을 만들지 않고 `complete: true`로 마무리한다.

## 저장과 화면 호환

- 기존 `Submission.feedback`과 `Submission.rounds` JSON 컬럼을 재사용한다.
- 면담 보고서 라운드에는 기준 판정, 미션의 루브릭/채점기준 ID, 내부 확인 기준을 함께 저장한다.
- 학생 화면은 미션 배열 길이 0~2개를 안전하게 표시한다.
- 학생에게는 내부 판정 용어와 `criterion`을 직접 노출하지 않는다.
- 재코칭은 직전 라운드에 저장된 미션과 `criterion`을 사용한다.
- 기존 장르의 저장 형식과 화면은 계속 동작해야 한다.

## 오류 처리

- Gemini의 JSON이 스키마와 맞지 않으면 해당 호출을 한 번 재시도한다.
- 재시도 후에도 실패하면 기존 사용자용 네트워크 오류 메시지를 반환하고 DB 라운드를 추가하지 않는다.
- 판정 결과에 기준 ID 누락, 중복, 알 수 없는 값이 있으면 유효하지 않은 응답으로 처리한다.
- `new-fact=unmet`, `fact-detail=met` 같은 금지된 논리 조합은 검증 단계에서 거부하고 재시도한다.
- 판정은 성공했지만 작문 호출이 실패하면 부분 결과를 저장하지 않는다.
- 무의미 글과 비속어 검토 흐름은 기존 동작을 유지한다.

## 평가 루프

### 평가셋

- 개발셋 12편: 프롬프트 수정 과정에서 매번 실행한다.
- 검증셋 8편: 후보 프롬프트가 개발셋을 통과한 뒤에만 실행한다.
- 우수 글, 일부 누락, 대부분 누락, 경계 사례, 구조만 뒤섞인 글, 무의미 글, 거의 수정하지 않은 글을
  포함한다.
- 각 글에는 사람이 정한 7개 기준의 기대 판정과 허용 가능한 수정 대상을 저장한다.

### 1단계 합격 조건

- JSON 스키마 성공률 100%.
- 개발셋의 기대 판정과 90% 이상 일치.
- 같은 글을 3회 실행했을 때 판정 일치율 95% 이상.
- 글에 없는 내용을 추측해 `met`으로 판정한 사례 0건.
- 금지된 논리 조합 0건.
- 준비된 무의미 글 사례 전부 통과.

### 2단계 합격 조건

모든 생성 미션이 다음 조건을 만족해야 한다.

- 선택된 루브릭과 채점기준에 직접 연결된다.
- 학생 글의 실제 내용에 근거한다.
- 핵심 결과 하나를 요구한다. 통합 미션은 그 결과를 위한 짧은 연속 단계만 허용한다.
- 무엇을 고칠지 바로 이해할 수 있다.
- 완성 문장이나 모범답안을 대신 쓰지 않는다.
- 글에 없는 사실을 만들지 않는다.
- 다른 미션과 사실상 중복되지 않는다.
- 초등학교 6학년에게 적절한 표현과 길이를 사용한다.

형식, ID, 개수, 금지 표현, 중복 후보는 자동 검사한다. 의미 품질은 사람이 평가한다.

### 종료 조건

- 모든 필수 조건을 만족한다.
- 검증셋 판정 정확도가 85% 이상이다.
- 전체 기존 단위 테스트와 프로덕션 빌드가 통과한다.
- 두 번 연속 프롬프트 수정에서 성능이 개선되지 않으면 프롬프트만 계속 고치지 않고 채점기준이나
  파이프라인을 다시 검토한다.
- 프롬프트 수정은 한 번에 한 가지 원인만 대상으로 하며 최대 8회 반복한다.

## 로컬 파일럿 실행

- `npm run dev`로 로컬 앱을 실행한다.
- `npm run eval`로 개발셋 또는 검증셋의 실제 Gemini 평가를 실행할 수 있게 한다.
- API 키가 없는 환경에서도 프롬프트 빌더, 선택 규칙, 스키마 검증, 평가 집계 테스트는 실행할 수 있어야
  한다.
- 실제 API 평가는 `GEMINI_API_KEY`가 설정된 경우에만 실행한다.
