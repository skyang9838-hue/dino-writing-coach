# 피드백 시스템 개편: 설계안과 지금 코드 비교

- **날짜**: 2026-10-12
- **단계**: 설계·진단 단계. 코드는 아직 바꾸지 않았다.
- **이 문서**: 선생님이 쓴 개편 설계안(맨 아래 부록)을 지금 코드와 맞대어 **유지할 것 / 바꿀 것 / 측정해서 정할 것**을 정리하고, 문답으로 정한 결정을 기록한다.
- **다음**: 측정(유료 Gemini 호출, 허락 받고) → 남은 두 가지 결정 → `docs/superpowers/plans/`에 구현 계획 → 별도 브랜치에서 구현

## 2. 지금 파이프라인

`lib/coaching.js` `getRubricCoachingFeedback`, 회차마다 Gemini를 2번 부른다.

1. **판정 호출** (`buildAssessmentPrompt`, temp 0): 채점기준 전체를 met/partial/unmet으로 판정하고, **같은 호출에서** 지난 미션의 done/partial/not-done도 판정한다. 프롬프트는 이전 글과 단어 diff까지 받는다. 글이 한 글자도 안 바뀌었으면 호출하지 않고 직전 판정을 쓴다.
2. **잠금** (`lib/assessmentRatchet.js` `ratchetAssessments`): 올라간 판정은 내려가지 않는다. 모델의 원래 판정은 `round.rawAssessments`에 남는다.
3. **코드가 미션 대상 2개를 고른다** (`lib/missions.js` `selectMissionTargets`): unmet → partial 순이고, 최근 두 회차 연속 나온 기준(`repeatedTwice`)은 뒤로 미룬 뒤 `priority` 순이다. 2개가 안 차면 `POLISH_TARGETS`(맞춤법·문장 다듬기)가 채운다.
4. **미션 호출** (`buildMissionPrompt`, temp 0.7, 최대 5회 재시도): 코드가 고른 대상, `missionSeed`, 지난 미션 수행 상태를 받는다. 응답은 `sanitizeMissionResult`(지어낸 인용 치환, 막연한 문장 제거, 막연한 제목은 `fallbackMissionTitle`로 교체)와 `validateMissionResult`(아래 5절의 검사들)를 거친다.
5. **도달도** (`lib/interviewRound.js` → `lib/attainment.js` `computeNextAttainment`): 첫 회차 40, 이후 지난 미션 done 하나당 +10, 상한 없음. 채점기준 점수 `actualAttainment`는 저장만 하고 도달도에는 쓰지 않는다.

## 3. 유지할 것

설계안 2절의 "반드시 유지할 구조"는 지금 코드가 이미 그렇게 돼 있다.

- 성취기준 → 청크 → 채점기준 구조와 `evaluator` 세 종류 (`lib/curriculum.js`, `getAiRubrics`)
- met/partial/unmet 판정, 교사 보드의 회차 카드와 기호 (`lib/revisionBoard.js`, `components/RevisionBoard.jsx`)
- 도달도와 채점기준 충족을 따로 계산하는 것 (`attainment` / `actualAttainment`)
- **도달도 공식 전체** (`lib/attainment.js`, `lib/mascot.js` 손대지 않음)
- 미션 수행 판정의 입력: 이전 글·현재 글, `summarizeWritingChanges`의 단어 diff, 지난 미션의 제목·설명·확인 기준 (설계안 5절과 같다)
- 미션 구성 `title`/`instruction`/`criterion`(= 제목·설명·확인 기준)
- 무의미 글 처리(`meaningless`, `discardNonsenseRound`), 글이 그대로면 다시 판정하지 않는 것, `rawAssessments` 기록
- 채점기준이 없는 단원의 일반 코치(`getGeminiFeedback`, `REVISION_SCHEMA`, 지금은 1단원). 1단원 기준이 들어오면 새 파이프라인을 탄다.

## 4. 바꿀 것

### 4.1 미션 생성 (설계안 3절·7절)

**지운다**
- `selectMissionTargets`와 `repeatedTwice`, `priority` 정렬 (`lib/missions.js`)
- `POLISH_TARGETS`와 글다듬기 분기 전부: `buildMissionPrompt`의 `polishBlock`, `hasIdenticalCorrection`/`CORRECTION_PATTERNS`, `sanitizeMissionResult`와 `validateMissionResult`의 polish 예외
- `targetIndex` 짝짓기 (`sanitizeMissionResult` 앞부분, `normalizedTargetKey` 대조)
- 미션 프롬프트의 "[코드가 선택한 수정 대상]"과 "[지난 수정미션 수행 상태]" (`priorMissionStatuses` 인자)
- `lib/curriculum.js` 각 기준의 `priority` 필드

**새로 한다**
- 미션 스키마(`buildMissionSchema`)의 각 미션에 `criterionId`(그 단원 AI 기준 id enum)를 넣는다. AI가 기준을 직접 고르고, 코드는 그 id가 진짜 기준인지만 확인한다. 저장 형식은 지금처럼 `rubricIds`/`criterionIds` 배열로 맞춰 둔다. 보드와 옛 회차가 그 모양을 읽기 때문이다.
- 프롬프트에 넣을 것: 기준별 판정 결과, 기준별 `missionSeed`(선생님이 쓴 방향), 설계안 원칙 세 가지. 첫째, unmet·partial을 모두 고려하되 무조건 unmet부터 고르지 않는다. 둘째, 개선 효과가 크고 실행하기 쉬운 곳을 먼저 고른다. 셋째, 한 번의 퇴고로 끝낼 크기로 만든다.
- 모자란 기준이 3개보다 적으면, 한 기준의 여러 곳을 짚거나 충족한 기준의 심화 미션을 섞는 것을 AI에게 맡긴다.
- 개수 2 → 3. 2가 박혀 있는 곳: `buildMissionSchema`(min/maxItems), `PRIOR_MISSION_SCHEMA`(maxItems), `sanitizeMissionResult`, `validateMissionResult`("항상 2개여야 함"), `missionRules` 첫 세 줄, 테스트(`lib/coaching.test.js`, `lib/missions.test.js`)
- **모두 met이면** 같은 호출에서 지시만 바꿔 심화 미션 3개를 낸다. 기존 기준 안에서 구체성·표현력·생동감·깊이를 다루고, 새 평가 기준을 만들지 않으며, 잘한 점을 충분히 칭찬한다. 추가 퇴고는 학생이 고른다.

### 4.2 채점기준 판정 (설계안 4절)

- `ratchetAssessments`를 "잠금"에서 "하락 확인"으로 바꾼다.
  1. 판정 결과를 직전 회차의 **최종** 판정과 비교한다.
  2. 내려간 기준이 없으면 그대로 쓴다. 추가 호출은 없다.
  3. 내려간 기준이 있으면 **하락 확인 호출**을 한 번 한다. 입력은 이전 글, 현재 글, diff, 내려간 기준(과 그 met/partial/unmet 설명)뿐이다. 기준마다 "관련 내용이 실제로 지워지거나 약해졌는가"를 true/false로 답한다.
  4. true면 하락을 반영하고, false면 이전 판정을 유지한다.
- 회차 기록에 하락 확인 결과를 남긴다. 예: `regressionChecks: [{ criterionId, from, to, regressed }]`. 보드 표시(4.6)의 근거가 된다.
- 하락 확인도 AI 판단이라 틀릴 수 있다. 그래도 지금처럼 잘못 올라간 판정이 영구히 굳는 일은 없어진다.

### 4.3 미션 수행 판정 (설계안 5절)

- `formatPriorMissionBlock`의 done 정의를 바꾼다. 지금은 "확인 기준을 분명히 만족하는 변화"인데, 설계안 표대로 관대하게 한다.
  - done: 미션 방향에 맞는 의미 있는 개선이 있다. 짧거나 서툴러도 요구한 행동을 했으면 done이다.
  - partial: 고친 흔적은 있지만 관련성이나 개선이 부족하다.
  - not-done: 미션과 관련된 수정이 없다.
  - 글자 수만 늘리기, 관계없는 내용 추가, 의미 없는 수정은 done이 아니다.
  - 확인 기준은 남기되, 미션 설명에 없던 요구나 지나치게 엄격한 조건을 덧붙여 판정하지 않는다.
- **학생이 고른 미션만** 판정 프롬프트와 `validateAssessment`의 기대 미션 id 목록에 넣는다.
- 코드는 미션 id와 응답 형식만 검사한다 (지금도 그렇다).

### 4.4 학생 화면

- `components/WritingScreen.jsx`: 미션을 받자마자 카드를 눌러 할 것을 고른다(1~3개). 1개 이상 골라야 "다시 코칭 받기"가 켜진다. 첫 회차 버튼 조건(목표 글자 수)은 그대로다. 다 충족해서 더 고치고 싶지 않은 학생은 그냥 멈추면 된다.
- 문구: `🎯 수정 미션 (N가지)` 아래에 "해 볼 미션을 골라요" 안내를 넣는다.
- `lib/actions.js` `requestCoaching(submissionId, writing)`에 `selectedMissionIds`를 더한다. 고른 정보는 `lastImprovements`와 `rounds`의 JSON 안에 둔다(미션마다 `selected`). **DB 마이그레이션은 필요 없다.**
- 서버는 고른 id가 직전 미션 id 안에 있는지, 1개 이상인지 확인한다.

### 4.5 도달도

공식은 바꾸지 않는다. `computeNextAttainment`는 그대로 `addressed`(done 여부 배열)를 받는다. 고르지 않은 미션은 판정하지 않으니 배열에 들어가지 않는다.

### 4.6 교사 보드

- 하락 `▼`가 다시 나온다. `lib/revisionBoard.js` `getTrend`는 이미 하락을 그릴 수 있으므로, 하락 확인을 거친 실제 하락만 최종 판정에 남으면 된다.
- **하락 확인으로 지킨 판정**(AI가 내렸지만 확인해 보니 글이 그대로라 이전 판정을 유지한 기준)에 작은 표시를 붙이고 범례에 추가한다 (`components/RevisionBoard.jsx`).
- 미션 칸에는 **학생이 고른 미션만** 그린다. 고르지 않은 미션은 판정이 없어서 보여 줄 상태가 없다. 고른 것과 안 고른 것을 구분해 보여 주는 표시는 따로 만들지 않는다.

## 5. 측정해서 정할 것 (다음 단계)

Gemini 실제 호출이라 비용이 든다. 사용자 허락을 받고 돌린다. 도구는 `npm run smoke`다. DB를 건드리지 않고, 판정 흔들림(`--runs`)과 거절 사유(`captureRetries`)를 이미 모은다.

1. **판정 흔들림** (설계안 8.1, 8.4): 같은 글을 `--runs 3`으로 돌려 일치율을 본다. 미션 수행 판정을 같은 호출에 둘 때와 따로 뗄 때를 비교한다. 코드 주석에는 판정 호출이 이전 글과 diff까지 받는 탓에 같은 267자 글이 다르게 읽혔다는 기록이 있다. 떼면 판정 호출이 지금 글만 보게 되지만, 회차마다 호출이 하나 는다.
2. **모델** (8.2): 스모크에 `--model` 옵션을 붙여(지금 `MODEL_ID` 상수) Flash-Lite와 상위 Flash를 비교한다. 판정 일치율, 미션 품질, 응답 시간을 본다.
3. **검증 규칙** (8.3): 규칙마다 거절 횟수를 세어, 남길 것과 프롬프트 지시로만 둘 것을 고른다. 지금 규칙과 생긴 이유는 아래와 같다.

   | 규칙 (`lib/coaching.js`) | 하는 일 | 생긴 이유 |
   |---|---|---|
   | 형식 검사 (개수·id·빈 값) | 응답 모양 확인 | 저장·보드가 이 모양을 읽는다. **반드시 남긴다** |
   | 잘한 점이 실제 met 기준을 가리킴 / 없으면 `effort` | 거짓 칭찬 막기 | 충족 안 한 기준을 칭찬하면 거짓말이 된다. rubricId 대조는 재시도의 큰 원인이라 이미 뺐다 |
   | `ACTION_TITLE_PATTERN` (제목 `-기` 목록) | 제목이 행동인지 | '이야기'처럼 -기로 끝나도 행동이 아닌 제목을 거르려고. 새 단원에서 '만들기'·'채우기'가 목록에 없어 5회 재시도 끝에 실패한 일이 있다 |
   | `ACTION_INSTRUCTION_PATTERN` | 설명에 동작이 있는지 | 행동할 수 없는 미션 막기 |
   | `hasForbiddenVaguePhrase`, `isVagueOnlyMission` (+ sanitize의 막연한 문장 제거, `fallbackMissionTitle`) | '자세히 쓰기' 같은 막연한 미션 막기 | 학생이 무엇을 할지 모르는 미션이 나왔다 |
   | 예시 문장 금지 (`예를 들어` 등) | 베낄 답 막기 | 코치가 답을 써 주면 퇴고가 아니게 된다 |
   | `hasUngroundedQuotedContent` (+ sanitize의 인용 치환) | 학생 글에 없는 말 인용 막기 | 모델이 학생이 쓰지 않은 문장을 인용했다. 치환 뒤 "학생 글의 관련 내용은…" 같은 어색한 문장이 생기는 부작용이 기록돼 있다 |
   | 면담 사실 지어내기 금지 | "듣지 못했다면 상상해 써" 막기 | 면담 보고서에서 사실을 지어내게 하는 미션이 나왔다 |

4. **교실 운영** (8.5): 회차당 호출 수는 판정 1 + 하락 확인 0~1 + 미션 1이고, 미션 판정을 떼면 +1이다. 응답 시간과 재시도 수로 24명 × 40분 수업의 대기 시간과 비용을 추산한다.

## 6. 그 뒤

측정 결과로 열린 두 가지(미션 수행 판정 위치, 검증 규칙)를 정한다 → 구현 계획을 쓴다 → **별도 브랜치**에서 구현한다(master push가 곧 배포라서). 구현 뒤에는 스모크를 다시 돌리고, `PROJECT_STATUS.md`의 "핵심 규칙" 표(매 라운드 미션 정확히 2개, 판정은 내려가지 않음)를 고친다.

## 부록: 선생님 설계안 원문 (2026-10-12)

> 아래는 받은 그대로 옮긴 것이다. 1절의 결정이 이 원문과 다를 때는 결정이 우선한다.

### 🦖 DINO 피드백 시스템 개편 설계안

#### 1. 개편 목적

현재 Gemini 2.5 Flash-Lite의 채점기준 판정이 회차마다 흔들리고, 코드 중심의 미션 선정으로 인해 개별화된 코칭에 한계가 있을 가능성이 있음.

**목표는 판정 안정성 향상, 학생 맞춤형 피드백 강화, 시스템 단순화.**

기존 구조를 무조건 교체하지 않고 필요한 부분만 개선한다.

#### 2. 반드시 유지할 구조

- **성취기준 → 성취기준 청크 → 채점기준** 구조와 교사가 직접 설계한 데이터는 변경하지 않는다.
- 채점기준별 met(충족) / partial(부분 충족) / unmet(미충족) 판정 유지.
- 교사 화면의 회차별 가로 카드 및 ✓ / ? / ✕ 표시 유지.
- AI는 학생을 평가하거나 점수화하는 도구가 아니라 퇴고를 돕는 코치.
- 학생의 도달도와 채점기준 충족 여부는 별개로 관리한다.

#### 3. 수정 미션 생성 방식 개편

**기존:** AI 판정 → 코드가 unmet·partial·priority 순으로 미션 대상 2개 선정 → AI가 미션 작성

**개편:** AI 판정 → AI가 채점기준과 학생 글을 종합해 미션 3개 직접 선정·작성

- AI는 반드시 교사가 설계한 채점기준 안에서 미션을 생성한다.
- unmet과 partial을 모두 고려하되, 무조건 unmet부터 선택하지 않는다.
- 학생의 글에서 가장 개선 효과가 크고 실행하기 쉬운 부분을 우선한다.
- 미션은 한 번의 퇴고로 수행할 수 있도록 작고 구체적으로 만든다.
- 학생에게 3개를 제시하고, 학생은 1~3개를 자유롭게 선택해 수행한다.
- 이전 회차 미션과 수행 결과를 참고해 불필요한 반복을 줄인다.
- 기존 코드의 priority 기반 선정과 복잡한 반복 방지 규칙은 제거 또는 단순화를 검토한다.

**미션별 구성**
- 제목: 무엇을 고칠지 간결하게 제시
- 설명: 학생이 실제로 무엇을 해야 하는지 안내
- 확인 기준: 어떤 변화가 있으면 성공인지 명시

확인 기준은 유지한다. 단, 미션 설명에 없는 새로운 요구나 지나치게 엄격한 조건을 추가하지 않는다.

#### 4. 채점기준 판정 안정화

현재는 판정이 한 번 met이 되면 이후 회차에서도 하락하지 않는 완전 잠금 방식이다.

**개편 방향: 독립 판정 + 하락 시 전후 비교**

1. 매 회차 현재 글을 채점기준에 따라 독립적으로 판정한다.
2. 이전 회차보다 판정이 하락하면 수정 전후 글을 비교한다.
3. 실제로 관련 내용이 삭제되거나 약화되었다면 하락을 반영한다.
4. 실제 퇴보가 확인되지 않으면 이전 판정을 유지한다.

목적은 AI의 단순한 판정 흔들림을 방지하면서도 잘못된 충족 판정이 영구적으로 고정되는 문제를 줄이는 것이다.

단, 전후 비교 역시 AI 판단이므로 정확성이 보장되지는 않는다. 추가 호출 여부, 응답 속도, 비용을 고려해 최소한의 구조로 설계한다.

채점기준 판정은 **교사 참고용**이며, 학생의 도달도 계산에는 직접 반영하지 않는다.

#### 5. 미션 수행 판정

현재 시스템의 기본 구조를 유지한다.

- AI가 이전 글과 현재 글 전체를 비교한다.
- 단어 단위 diff로 추출한 추가·삭제 부분도 제공한다.
- 이전 미션의 제목·설명·확인 기준을 함께 제공한다.
- AI가 done / partial / not-done으로 판단한다.
- 코드는 미션 ID와 응답 형식 등 최소한의 검증만 담당한다.

**핵심 변경: 미션 수행 판정을 관대하게 한다.**

| 상태 | 판단 기준 | 도달도 |
|---|---|---|
| done | 미션 방향에 맞는 의미 있는 개선이 확인됨 | +10%p |
| partial | 수정 흔적은 있지만 관련성이나 개선이 부족함 | 변화 없음 |
| not-done | 미션과 관련된 수정이 없음 | 변화 없음 |

완벽한 문장이나 높은 글쓰기 수준을 요구하지 않는다. 미션에서 요구한 행동을 적절하게 수행했다면 짧거나 표현이 서툴러도 done으로 인정한다.

단순한 글자 수 증가, 무관한 내용 추가, 의미 없는 수정은 성공으로 인정하지 않는다.

#### 6. 도달도 시스템

도달도는 **글의 완성도 점수가 아닌 퇴고 과정의 동기부여 지표**이다.

- 시작 도달도: 40%
- 미션 1개 성공: +10%p
- 한 회차에서 최대 3개 성공 가능
- 회차가 바뀌어도 누적 유지
- 최대 도달도: 100%
- partial / not-done은 상승 없음
- 같은 수정 행동을 중복 인정해 도달도를 반복 상승시키지 않도록 한다.

학생이 퇴고를 통해 실제로 글을 개선했다면 가능한 한 긍정적으로 인정한다.

#### 7. 모든 채점기준을 충족한 경우

모든 기준이 met인 학생에게도 코칭을 제공하되, 부족한 점을 억지로 만들어내지 않는다.

**일반 보완 미션 → 선택형 심화 미션으로 전환**

- 기존 채점기준과 연결된 발전 미션 3개 제시
- 글의 구체성, 표현력, 생동감, 내용의 깊이 등을 발전시키는 방향
- 새로운 평가 기준을 임의로 추가하지 않음
- 이미 잘 썼다는 점을 충분히 칭찬하고 추가 퇴고는 학생이 선택
- 심화 미션을 성공적으로 수행하면 동일하게 +10%p 인정

별도의 복잡한 심화 시스템을 만들기보다 기존 미션 생성 과정에서 처리한다.

#### 8. 구현 전 검토 사항

1. **판정 안정성:** 동일한 학생 글과 채점기준으로 반복 판정했을 때 결과가 얼마나 일치하는가?
2. **모델 비교:** Gemini Flash-Lite와 상위 Flash 모델의 판정 일관성 및 미션 품질 차이는?
3. **프롬프트 단순화:** 기존 채점기준별 판정 지침, 미션 지침, missionSeed, 검증 규칙 중 실제 필요한 요소는 무엇인가?
4. **하락 판정:** 전후 비교를 통한 재확인이 판정 흔들림을 실질적으로 줄이는가?
5. **수업 운영:** 24명 학생이 40분 수업에서 사용해도 응답 속도와 API 비용이 적절한가?

#### 9. 최종 설계 원칙

**교사가 기준을 설계하고 → AI가 학생 글을 분석해 맞춤 미션을 제안하고 → 학생이 선택해 퇴고하고 → AI가 개선을 확인한다.**

- 채점기준은 고정하되 피드백은 개별화한다.
- 채점기준 판정은 안정적이고 정확하게 한다.
- 미션 수행 판정은 관대하게 한다.
- 도달도는 학생의 성장을 격려하는 장치로 사용한다.
- 불필요한 코드 규칙과 중복 로직은 최소화한다.

**현재는 설계·진단 단계다. 바로 구현하지 말고, 기존 코드와 비교해 변경할 부분 및 유지할 부분을 먼저 정리한다.**
